# Миграция IMAP — r9 / 0.2.0

## Обновление существующего Portainer stack

1. Дождитесь завершения активного SSH-экспорта и остановите worker на время обновления.
2. Сохраните резервную копию SQLite: остановите web и worker и скопируйте volume dbdata
   целиком (в том числе WAL/SHM, если они есть). Сохраните имеющийся APP_SECRET_KEY.
3. Обновите файлы проекта из полного архива r9, включая новые app/, tests/ и migrations/.
4. Пересоберите и пересоздайте web и worker. Сборка без кэша не обязательна:
   изменение pyproject.toml добавляет пакет IMAPClient. Имя stack и volumes не меняйте.
5. APP_SECRET_KEY оставьте прежним. NAS_MOUNT_PATH должен указывать на подключённую
   шару, в вашей установке `/mnt/synology-pst`, а не на `./nas`.
6. Откройте http://server:8085 и раздел «Миграция IMAP».

Схема добавляется автоматически под блокировкой SQLite; SQL для проверки находится
в migrations/002_imap.sql. Выполнять его вручную при обычном обновлении не нужно.
Новых переменных .env нет. Мастер начальной настройки может быть пройден без
заполнения SSH-подключения, если используется только IMAP.

## Первый запуск

В «Настройки» проверьте NAS, рабочий каталог и резерв свободного места.
Для начала используйте один небольшой реальный ящик. В разделе IMAP укажите
сервер, порт, TLS (обычно 993) или STARTTLS (обычно 143). Проверка сертификата
обязательна. Вход — пользовательский пароль или пароль приложения, если провайдер
его требует. OAuth/SSO без пароля в этой версии не реализованы.

Выберите хранилище и одну/обе галочки: Zimbra TGZ, Outlook PST. Загрузите CSV,
нажмите «Проверить CSV», затем «Добавить в очередь». Подключение и проверка пароля
выполняются worker по очереди, без сотен одновременных входов. Ошибка одного ящика
не останавливает остальные.

CSV UTF-8, с BOM или без, запятая или точка с запятой:

```csv
email,password,target_email
user@old.ru,"password,with;separators",user@new.ru
```

target_email необязателен: задаёт имя нового PST-хранилища и имена файлов, но
не переписывает отправителей, получателей или содержимое писем. Пароль сохраняется
точно, включая пробелы. Кавычка внутри поля CSV удваивается. Пример с вымышленными
данными — examples/imap-accounts.csv. Неверный CSV отклоняется целиком, без частичной
постановки. Повторная отправка той же формы не дублирует пакет.

CSV передаётся телом запроса, не в URL и не multipart-файлом; сервер не сохраняет
его на диск. Пароли шифруются Fernet. Список, отчёты и журналы приложения их не
возвращают. Используйте защищённый доступ к Web UI (HTTPS через ваш reverse proxy).

## Загрузка и продолжение

- По умолчанию работает один worker: не масштабируйте его. Linux-блокировка на
  dbdata защищает от запуска двух worker над одной базой. Одна активная конвертация
  уменьшает риск прежних ошибок нехватки памяти.
- IMAP открывает папки только для чтения (EXAMINE) и использует BODY.PEEK. Состояние
  прочтения на исходном сервере не меняется. Команды удаления не отправляются.
- LIST читает папки, UID SEARCH — сообщения, FETCH — размер, INTERNALDATE и флаги.
  Скачивание тела идёт частями по 1 МиБ; все письма ящика в память не загружаются.
- База хранит папку, UIDVALIDITY, UID, размер, дату, флаги и SHA256. Файл публикуется
  после fsync, затем фиксируется запись SQLite. После обрыва скачанное повторно
  не передаётся; незавершённое письмо скачивается сначала.
- Изменение UIDVALIDITY вызывает пересканирование. Старые исходные файлы остаются
  на хранилище, но исключаются из нового снимка по поколению сканирования.
- Временные обрывы повторяются с задержкой до 30 минут; после 8 автоматических
  повторов нужна кнопка «Повторить». Ошибка авторизации/сертификата сразу показывается.
- Недостаток места — WAITING_FOR_SPACE; недоступность/права хранилища —
  WAITING_FOR_STORAGE. Нужен резерв как на NAS, так и на рабочем диске для PST.
  Linux-проверка монтирования не доказывает, что bind mount действительно ведёт на
  NFS: проверяйте подключение NAS на Docker-хосте. Жёсткий NFS mount может задержать
  операцию на время восстановления сети.
- «Отменить» останавливает работу на ближайшей контрольной точке; сетевой таймаут
  до 60 секунд. Во время PST завершается группа процессов конвертера.

## Результаты

Структура хранения:

```text
/data/nas/imap-migrations/<уникальный-id>/
  source/<папка-хеш>/<uidvalidity>/<uid>.eml
  folders.json
  manifest.jsonl
  export-1/
    ГГГГММДД-user@domain.ru.tgz
    ГГГГММДД-user@domain.ru.pst
    report.json
```

Дата в имени — дата создания задачи UTC. Служебные уникальные каталоги исключают
перезапись одноимённых файлов; номера задачи в имени самого файла нет.
TGZ доступен для скачивания, даже если PST не получился. При повторе готовый TGZ
не пересобирается. Если PST готов локально, но места на NAS не хватает, последующий
запуск копирует этот PST без повторной конвертации. Копия проверяется по SHA256.
Для режима только PST TGZ используется как внутренний промежуточный файл.

Срок PST — 14 дней с его создания. Скачивание после срока закрывается, worker
удаляет его при следующем проходе очистки, включая PST прошлых поколений.
Исходники и TGZ миграции сохраняются до ручной проверки. Кнопка «Удалить файлы»
удаляет все данные конкретной миграции, её пароль и рабочие файлы; история остаётся.
Это необратимая операция без отдельной резервной копии. «Забыть пароль» удаляет
только сохранённый секрет. До завершения дозагрузки пароль может понадобиться.

«Дозагрузить» делает новый проход по источнику и новый **полный** экспорт в
export-2, export-3 и т.д. Уже скачанные неизменившиеся UID не передаются повторно.
Это не дельта-архив для наложения на заполненную Zimbra: повторный штатный импорт
полного TGZ может дублировать письма. Для окончательного переезда используйте
последний полный экспорт в отдельный пустой целевой ящик.

## Точность переноса и ограничения

TGZ импортирует почту, структуру непустых папок, даты получения и состояние
прочтения. Кириллица, вложенные папки и вложение проверены пользователем на Zimbra
8.8.15 на тестовом архиве. Это не полная резервная копия аккаунта: папки без писем
перечисляются в folders.json, но импортом не создаются. Флаги «важно», «отвечено»,
«черновик», пользовательские метки сохраняются в manifest.jsonl, но не в TGZ.
Системные папки сопоставляются по INBOX и SPECIAL-USE; без этих признаков их
названия сохраняются. Неподдерживаемые символы имён папок экранируются.

Контакты, календари, правила и подписи по IMAP не загружаются. Встречи, прикреплённые
к письмам, остаются вложениями. TGZ хранит исходные MIME-байты без нормализации.
Рабочая копия для PST проходит существующий адаптер кодировок. ContinuMail остаётся
экспериментальным: полноту отображения метаданных и флагов PST проверяйте в Outlook.
Встроенная проверка PST — результат конвертера, число сообщений, сигнатура и SHA256,
а не независимая проверка всего содержимого Outlook.

При очередной дозагрузке письма, удалённые с источника, остаются среди исходников,
но не входят в новый снимок. Одновременно изменяющийся источник не даёт гарантии
единого момента снимка: перед финальной миграцией остановите работу пользователей
и выполните последний проход.

## Проверки этой сборки

Тесты: `python -m pip install -e ".[test]"` и `python -m pytest -q`.
Включены TCP IMAP-стенд с настоящим IMAPClient (обрыв, ranged FETCH, modified UTF-7),
сохранность байтов, даты/прочтение TGZ, UIDVALIDITY, повреждение локального файла,
239 строк CSV, шифрование, повторная отправка формы, CSRF, частичный сбой PST,
удаление PST по сроку и сохранение существующей SQLite-истории при обновлении.
Для теста обработки сбоя PST writer заменяется тестовой функцией; реальная
конвертация/Outlook и Docker-сборка в текущей локальной Windows-среде не запускались.
Интерфейс проверен в headless Edge: вход, preview CSV, очередь и поиск.
