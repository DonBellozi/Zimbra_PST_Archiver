# Zimbra PST Archiver — MVP

Компактный Docker-сервис для постановки экспорта одной или нескольких учетных записей Zimbra 8.8.15 в устойчивую очередь, создания TGZ на Zimbra по SSH, контроля места, переноса промежуточного архива на NAS и последующей конвертации в PST. Web UI работает на порту **8085**, история и настройки сохраняются в локальном файле SQLite.

## Быстрый запуск

1. Создайте `APP_SECRET_KEY` указанной в `.env.example` командой. При обычном запуске Compose его можно положить в `.env`; в Portainer добавьте значение в **Stack → Environment variables**. Сам файл `.env` не обязателен.
2. Если нужен NAS, смонтируйте SMB/NFS на Docker-хосте и задайте абсолютный `NAS_MOUNT_PATH` в `.env`. Монтирование на хосте намеренно отделено от приложения.
3. Запустите `docker compose up -d --build`.
4. Откройте `http://server:8085` и пройдите мастер: создайте администратора, укажите SSH-доступ к Zimbra, каталоги и политику места.

### Portainer

Перед развертыванием stack добавьте переменную окружения `APP_SECRET_KEY` со сгенерированным Fernet-ключом. Compose намеренно не использует директиву `env_file`, поэтому Portainer не требует загружать отдельный `.env`. `NAS_MOUNT_PATH` можно добавить там же; без него используется локальная папка `./nas` проекта stack.

`.env` содержит только bootstrap-параметры контейнеров: мастер-ключ шифрования и bind mount NAS. Zimbra, storage, NAS, очередь и конвертер настраиваются в браузере. Пароли, приватный ключ, SHA256 fingerprint SSH-хоста и команда конвертера хранятся в SQLite в зашифрованном Fernet-виде и повторно в UI не показываются. SSH-подключение отклоняется, если fingerprint не совпадает. Резервируйте `APP_SECRET_KEY`: без него секреты нельзя восстановить.

База находится в Docker volume `dbdata` по пути `/data/db/archiver.sqlite3`. Включены WAL, foreign keys, `busy_timeout=30s` и нормальная синхронизация. Отдельный сервер БД, порт и пароль не нужны. Для резервного копирования используйте SQLite Online Backup либо остановите оба контейнера и скопируйте volume целиком.

При старте контейнер назначает приложению права на каталоги named volumes, после чего запускает Web UI/worker от непривилегированного пользователя `archiver` (UID 10001). Это устраняет `sqlite3.OperationalError: unable to open database file` на новом volume.
Каталог NAS намеренно не получает `chown`: права SMB/NFS или bind mount должны разрешать запись UID 10001 на Docker-хосте.

## Как работает задача

Worker по умолчанию один. Он получает размер mailbox (`zmmailbox gms`), проверяет свободное место Zimbra, формирует TGZ через `getRestURL '//?fmt=tgz'`, получает фактический размер через `stat`, проверяет локальное место, скачивает архив и запускает writer. Если локального места нет, но NAS доступен, TGZ сразу скачивается на NAS и задача получает `STORED_ON_NAS`; позднее она автоматически продолжится без повторного экспорта. Нехватка места дает `WAITING_FOR_SPACE`, не `FAILED`.

После успешной проверки PST локальная и удаленная копии TGZ удаляются. PST всегда истекает через 14 дней; бессрочного режима нет. Запись задачи и журнал состояний остаются, а статус меняется на `EXPIRED`.

## Настоящий PST

Проект **не создает фиктивный файл с расширением `.pst`**. В Linux нет зрелого свободного writer’а, который можно разумно заявить надежным для production: `libpff` предоставляет доступ/чтение PFF, а write-функциональность остается незавершенной. Сам формат сложен и нормирован Microsoft в MS-PST.

В MVP writer изолирован командным контрактом. В настройках задайте команду исполняемого конвертера; worker добавит к ней два аргумента:

```text
/opt/pst-writer/bin/convert [его параметры] /data/work/<id>/mailbox.tgz /data/pst/<id>-<account>.pst
```

Команда обязана создать настоящий Unicode PST. Затем сервис проверяет минимальный размер и сигнатуру `!BDN`. Для эксплуатации можно собрать отдельный образ поверх этого Dockerfile с лицензированным SDK (например, Aspose.Email) либо собственным writer’ом. Лицензия не включена. Пока команда не настроена, задача честно получает `FAILED`, объясняет причину и сохраняет TGZ; после настройки нажмите «Повторить».

Ссылки: [официальная спецификация MS-PST](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-pst/141923d5-15ab-4ef1-a524-6dce75aae546), [libpff](https://github.com/libyal/libpff).

## API и эксплуатация

- `GET /health` — readiness endpoint.
- `GET /api/accounts?q=` — поиск учетных записей через `zmprov -l gaa`.
- `POST /api/jobs` с `{"accounts":["user@example.org"]}` — массовая постановка.
- `POST /api/jobs/{id}/retry|cancel|delete` — действия.
- `GET /jobs/{id}/download` — скачивание только готового PST.

Удаление задачи удаляет связанные локальные/NAS-файлы и историю этой задачи. Отмена кооперативная: уже выполняющийся удаленный экспорт нельзя безопасно оборвать мгновенно, но worker остановится на следующей границе этапа.


SQLite-схема для управляемого развертывания находится в `migrations/001_initial.sql`. В MVP приложение также идемпотентно создает отсутствующие таблицы при старте.

## Границы MVP

- Один экземпляр worker обеспечивает заданную concurrency=1. SQLite подходит для этого режима; не масштабируйте worker до добавления lease/watchdog или перехода на серверную БД.
- Прогресс этапный, поскольку Zimbra REST export и внешний writer не публикуют универсальный byte-progress.
- Проверка PST базовая (сигнатура и размер). Для production добавьте open/read verification тем же SDK writer’а и тестовое открытие в целевой версии Outlook.
